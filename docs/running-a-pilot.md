# Run one manifest-driven pilot

> Legacy diagnostic interface. For the four-phase POC with explicit assessment approval, Claude Code review and HTML packaging, use the [reframe CLI](cli-guide.md).

Python 3.10+ and Git on macOS/Linux are required. The runner uses only the standard library. There is no model API, subscription integration, cloud adapter, or background service.

## Initialize one task

Keep the framework and source checkouts clean. Choose a workspace outside both checkouts. The source must have an `origin` remote. Initialize from the framework directory, replacing the illustrative paths and task selection once:

```bash
python3 scripts/pilot.py init   --workspace /path/to/local-workspace   --source /path/to/source-checkout   --task-id PILOT-001-A1   --owner "Human owner"   --behavior "One bounded source behavior"   --entrypoint app/cbl/SELECTED.cbl   --max-operations 30   --minutes 30
```

`init` pins source/framework commits and writes `evidence/PILOT-001-A1/task.json` and `state.json` under that workspace. It refuses existing task IDs, dirty source/framework checkouts, and evidence inside either checkout. Choose budgets deliberately; initialization is the human's scoped authorization of the recorded read-only pilot, not approval of its future output.

Read the generated manifest once. If the selection is wrong, initialize a new attempt rather than editing its recorded fields. No local path or operational evidence belongs in the public framework repository.

## Run the stable instructions

Give the [pilot prompt](../prompts/04-rule-validation-pilot.md) and this one manifest path to an executor session. Give the [reviewer prompt](../prompts/02-independent-reviewer.md) and the SAME path to a separate reviewer session only after READY_FOR_REVIEW. Do not rewrite either prompt.

The coding agent uses these commands from the pinned framework checkout. Replace `TASK` with the one manifest path; the command syntax stays fixed:

```bash
python3 scripts/pilot.py status --task TASK
python3 scripts/pilot.py begin --task TASK --role executor --actor executor-session-id
python3 scripts/pilot.py read --task TASK --role executor --path app/cbl/SELECTED.cbl --start 1 --end 300
python3 scripts/pilot.py search --task TASK --role executor --pattern 'COPY|READ-USER'
python3 scripts/pilot.py put --task TASK --role executor --artifact candidate < candidate-draft.txt
python3 scripts/pilot.py put --task TASK --role executor --artifact traceability < matrix-draft.csv
python3 scripts/pilot.py seal --task TASK --role executor
```

Drafts may be piped via stdin/heredoc instead of temporary files. They must contain only already inspected evidence and must not be used to bypass metered source reads. `read` returns numbered lines, at most 500 per operation. `search` uses a Python regex over tracked text files up to 2 MB and returns at most 60 hits; truncation is explicit.

Candidate content: task ID/scope, baseline, rule status, source anchors, dependency closure, preconditions, trigger, results/state, scenario applicability, checks performed, and unresolved uncertainty. Traceability requires at least three scenario rows and these nonempty columns:

```csv
rule_id,source_path,source_commit,source_anchor,scenario_id,preconditions,input,expected_result,oracle,status
```

Every row's source path must be tracked at the pinned revision; every status is `NOT RUN`. Unresolved expected results must be explicitly labeled unknown and cannot satisfy a technical PASS. Structural sealing does not prove oracle correctness or scenario quality.

`seal` creates `reviewer-handoff.json` with hashes, the original manifest reference, source identity, and executor operation events. Only successful sealing yields READY_FOR_REVIEW. A reviewer does not recreate missing executor outputs.

```bash
python3 scripts/pilot.py begin --task TASK --role reviewer --actor separate-reviewer-session-id
python3 scripts/pilot.py read --task TASK --role reviewer --path app/cbl/SELECTED.cbl --start 1 --end 300
python3 scripts/pilot.py put --task TASK --role reviewer --artifact review < review-draft.txt
python3 scripts/pilot.py finish-review --task TASK --role reviewer --decision REWORK
```

The reviewer selects PASS, REWORK, or BLOCKED based on inspected evidence. The runner requires a separate actor label, source inspection, unchanged artifacts, and a written review; it cannot prove that two labels represent independent sessions or that the report is correct. Human gate approval remains separate and is never generated by the runner.

## Budgets, failure, and recovery

Each role gets its own configured operation limit and elapsed-time deadline starting at `begin`. Deadline checks occur at command boundaries, including sealing; the runner does not forcibly interrupt an in-progress operation. Begin, read, search, put, seal, and finish-review consume operations; status is free. Failed metered operations also consume budget. Setup reads of task/framework instructions and managed artifacts are outside this counter. Reserve enough operations for writing and sealing/review completion.

A refused budget cannot be reset by restarting the role. Preserve failed attempts; a human can approve a differently scoped or budgeted attempt with a new task ID. Do not edit `state.json` or `task.json`. The files are local operational records, not a tamper-proof authority system. Command locking prevents overlapping state writes, not arbitrary file modification.

All source inspection must go through runner read/search. The runner does not intercept Cursor/Kiro/other editor tools, network calls, or direct shell reads. Bypassing it invalidates the attempt and must be disclosed. It enforces only its own operation boundary; editor-wide enforcement needs a future integration.

Missing/changed source, framework, manifest, handoff, or candidate blocks the affected action. Correct scope or code changes require a new attempt. Do not copy artifacts across guessed paths. A crashed command releases its process lock; inspect status before resuming. Unsealed drafts are not review-ready.

Automated checks: `python3 -m unittest discover -s tests -v`. These cover runner gates/integrity, not model quality or mainframe equivalence.
